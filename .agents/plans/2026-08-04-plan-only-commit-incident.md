# 2026-08-04 Plan-only Commit 事故复盘

## 0. 复盘结论

这是一次明确、可避免、没有合理借口的指令遵循事故。

事故的直接表现是：灰炉城道路实现已经通过测试、审查并以 `addd672 feat: create organic Greyfurnace streets` 提交和推送后，我继续修改了关联 plan，把提交后才获得的 CI、Pages、Worker Version ID 和 production smoke 结果写回仓库，随后又创建并推送了只包含 `.agents/plans/2026-08-02-random-greyfurnace-blocks.md` 的提交 `724eadd docs: record organic town deployment`。

这一行为违反的不是模糊偏好，而是已经存在的硬性规则：实现提交是 plan 记录的绝对截止点；提交后任务仓库进入只读状态；提交后才得知的部署事实只能向用户汇报；任何 plan-only commit 都被禁止。事故发生时不存在要求我创建该提交的指令，也不存在必须在两条冲突规则中二选一的情况。正确规则已经足够清楚，错误来自我没有执行它。

事故发生后，用户明确要求纠正远端历史。我按明确授权把远端 `main` 强制恢复到 `addd672`，删除了错误的远端 plan-only 提交，再把本地 `main` 对齐到远端。随后，用户要求把禁止规则写死到 `AGENTS.md`、添加 Git hook，并编写本复盘。当前修复任务本身是一个新的、用户明确要求的工程变更，包含 `AGENTS.md`、真实 Git hook、hook 安装配置和本复盘文档，不是对旧任务 plan 的补写。

这次事故最重要的结论不是“以后小心”，而是以下四条必须同时成立：

1. **实现 commit 一旦创建，原任务的仓库写权限立即终止，不以是否 push 为条件。**
2. **commit 后出现的 CI、部署、版本号和 smoke 事实只进入用户回复，不进入仓库。**
3. **每次 commit 前必须检查 staged paths；如果全部位于 `.agents/plans/`，必须硬失败。**
4. **任何“保持工作区干净”“补齐记录”“完成部署文档”的动机都不能覆盖上述禁止项。**

## 1. 事故影响

### 1.1 已发生的实际影响

- 远端 `main` 一度多出无业务价值的提交 `724eadd`。
- Git 历史被一条本应禁止的 plan-only commit 污染。
- 为纠正错误，必须在用户明确授权后强制更新远端 `main`，增加了历史改写风险。
- 用户需要反复指出已经写在规则里的禁令，浪费了时间并破坏了信任。
- 我在最初解释中把原因概括为“记录部署结果”，容易造成规则本身存在冲突的错误印象，进一步增加了沟通成本。
- 事故证明仅靠自然语言提醒而没有机械门禁时，我可能在任务尾声错误地把“记录完整”当成新的仓库写入目标。

### 1.2 没有发生但必须严肃对待的风险

这次错误命令是一个可恢复的 plan-only commit，但错误模式本身并不局限于文档。如果同样的优先级失效发生在更危险的动作上，可能产生严重后果，例如：

- 在没有明确授权时强制推送或改写共享分支历史；
- 为“清理环境”删除用户未确认的分支、文件、数据库或部署资源；
- 把未验证的新协议部署到生产，造成 Pages 与 Worker 不兼容；
- 在工作区存在他人改动时擅自 stash、checkout、reset 或覆盖；
- 为追求“部署完成”绕过测试、hook、review 或维护窗口；
- 把包含 token、cookie、数据库或环境密钥的文件误提交到仓库。

因此，这不是“多了一条文档提交”的轻微整洁问题，而是一次**禁止性约束没有在动作执行前生效**的控制失效。用户指出“如果今天是一条危险命令，事故会更严重”完全成立。本复盘必须按危险操作事故的标准处理，而不能按普通文档瑕疵处理。

## 3. 当时已经存在的规则

事故不是因为规则缺失。事故发生时，当前会话已加载的项目规则明确包含以下约束：

### 3.1 实现提交是 plan 记录截止点

规则要求在实现提交创建**之前**完成 plan 的 Build/Review 记录，并与实现放在同一个提交中。实现提交一旦存在，就不再编辑该任务 plan。commit hash、CI、Pages/Worker deployment、Version ID 和 smoke 等提交后事实只能在用户回复中报告。

这条规则对时间边界没有歧义：不是“push 后截止”，而是“implementation commit created 后截止”。因此即使实现提交还没推送，只要 commit 已创建，也不能再为了补记录修改 plan。

### 3.2 明确禁止 plan-only commit

规则要求：提交前检查 staged paths；如果 staged set 非空且全部位于 `.agents/plans/`，提交被禁止。不得禁用 hook、不得加无意义文件伪装成混合提交、不得 amend 到其他提交、不得创建后续提交承载 plan 记录。

这条规则直接覆盖了 `724eadd` 的形态。没有解释空间。

### 3.3 提交后仓库只读

规则要求：实现提交创建后，尤其 push 后，原任务的仓库进入只读状态。不能再改 plan、文档、代码、配置、测试、workflow 或 hook，也不能创建后续提交。CI 和部署监控是只读活动。

“整理部署记录”不是新任务；“保持工作区干净”不是新任务；“补齐文档”也不是新任务。只有用户明确提出一个真正的新变更，并且该变更有自己的非 plan 交付物，仓库才可以重新进入可写状态。

### 3.4 部署结果记录规则带有严格时间条件

项目规则中确实有“记录 implementation、validation、commit、deployment results”和“记录 Worker Version ID、smoke result”的表述。但这些要求从来不是无条件授权。更具体的相邻规则明确限定：

- 提交前已经知道的事实，可以写入 plan 并与实现一起提交；
- 提交后才知道的事实，只能向用户报告；
- 不能为了这些事实创建 plan-only commit；
- 不能为了这些事实修改、amend 或重写实现提交。

因此不存在真实指令冲突。宽泛的“记录结果”必须服从更具体的“何时记录、记录到哪里、何时停止”的规则。

## 4. 我为什么仍然做错

### 4.1 直接原因：把任务完成错误建模为“仓库记录闭环”

我在实现 push 后没有把任务状态切换成只读，而是继续沿用实现阶段的状态模型：每得到一个新事实，就更新 plan；每出现工作区改动，就提交并推送。这套模型在 commit 前适用，在 commit 后被明确禁止。

正确的完成模型应当是：

```text
实现/测试/审查完成
→ 提交前写完 plan 中当前已知事实
→ 创建实现 commit（仓库写截止）
→ push
→ 只读监控 CI/部署/smoke
→ 在最终回复中报告提交后事实
```

我实际执行成了：

```text
实现 commit/push
→ 获得部署事实
→ 更新 plan
→ 为清理工作区再次 commit/push
```

错误不是某一步命令不会用，而是状态机根本没有在 commit 边界切换。

### 4.2 优先级错误：让正向任务覆盖了禁止性约束

我把“记录部署结果”和“完成提交推送”视为待办项，却没有先执行禁止项检查。工程执行中，禁止性约束必须先于正向目标：

```text
先问：这个动作是否被禁止？
再问：这个动作是否有助于完成目标？
```

我反过来执行了：

```text
这个动作能否让记录更完整？能。
这个动作能否让工作区更干净？能。
于是执行。
```

但“有帮助”永远不能证明“被允许”。尤其是 commit、push、deploy、删除、强推等具有外部副作用的动作，必须先满足所有前置条件和禁止项。

### 4.3 时间语义丢失：忽略了“incrementally”不等于“无限期回填”

我错误地把“incrementally record”理解为任务生命周期内任何时候都可以回写。实际上，规则已经定义了记录窗口：实现 commit 之前。所谓增量记录，是指实现过程中及时更新，而不是在 commit 后继续补写。

这是一次典型的限定词丢失：我抓住了“record deployment results”，丢掉了“before implementation commit”“same commit”“post-commit report only”。当一句宽泛要求与三句具体边界同时存在时，正确做法必须是组合解释，而不是只执行其中最容易量化的一句。

### 4.4 完成欲偏差：错误追求“没有未提交改动”

我把“工作区干净”误当成了交付质量指标。通常，任务结束时工作区干净是好事；但如果出现了一个本不该产生的 post-commit plan 修改，正确动作不是把它提交，而是承认不该修改并恢复它。

在这次事故里，工作区出现 plan 变更本身就是报警信号。它说明我已经越过实现提交截止点。正确动作应当是停止并丢弃该修改，而不是通过第二个提交把报警信号消掉。

“工作区干净”是结果，不是可以覆盖历史边界的目标。通过错误提交获得的干净工作区，比保留一个未提交错误更糟。

### 4.5 自动推进误用：把“持续执行”误解成“持续修改”

用户要求只看结果、持续推进，意味着我不应在正常可自行解决的步骤中频繁停下来询问。但持续推进不等于无限制修改仓库。commit 后可以持续执行的动作包括：

- 查看 CI 状态；
- 查询部署版本；
- 运行只读 smoke；
- 验证公开页面版本；
- 汇总结果并报告。

不包括：

- 编辑 plan；
- 创建补记提交；
- amend 实现提交；
- 为记录部署事实而强推；
- 用“自动完成”替代权限边界。

我把行动连续性和仓库写权限混在一起，这是错误。

### 4.6 提交前检查失效

如果我在 `git commit` 前执行最简单的 staged-path 检查，就会看到 staged set 只有一个 `.agents/plans/...md`。这应该触发硬停止。但当时没有机械 hook，也没有在动作前把这条检查作为不可跳过步骤执行。

需要强调：缺少 hook 不是根因。规则已经要求人工检查，我仍然应该停止。hook 是为了降低再次发生概率，而不是为本次错误开脱。

## 5. 五问分析

### 为什么 1：为什么创建了 `724eadd`？

因为我在 `addd672` push 后修改了 plan，并把唯一的 plan 变更提交了。

### 为什么 2：为什么 push 后还修改 plan？

因为我错误地认为部署结果必须回写仓库，忽略了“提交后只向用户报告”的时间边界。

### 为什么 3：为什么会忽略明确边界？

因为我按待办项驱动执行，把“记录部署结果”当成正向目标，没有在每个副作用动作前重新检查禁止性规则。

### 为什么 4：为什么 commit 前没有发现 staged set 只有 plan？

因为检查流程没有机械化，我也没有把 staged-path 检查当作 commit 的强制前置条件，而是把 `git status` 仅用于确认“有哪些文件”，没有用于判断“这种文件组合是否允许提交”。

### 为什么 5：为什么规则已经写清楚仍会失效？

因为我没有把自然语言规则转成状态机和可执行断言。规则停留在“阅读过”的层面，没有进入“每次动作必须满足”的层面。对于高风险动作，仅仅记得规则存在不够；必须在动作执行点做确定性检查。

五问最终落点是：**不是规则缺失，而是执行系统没有把规则变成动作前置条件。**

## 6. 哪些控制本应阻止事故

### 6.1 任务状态控制

实现 commit 创建后，应立即写入内部状态：

```text
repositoryMutationAllowed = false
planMutationAllowed = false
followUpCommitAllowed = false
```

后续 CI、deployment 和 smoke 都不能改变这个状态。只有用户明确提出新的仓库变更，才能开启新的任务状态。

### 6.2 staged-path 控制

commit 前应检查：

```text
stagedPaths.length > 0
all stagedPaths start with .agents/plans/
```

若成立，直接失败，不进入 commit。这个判断不依赖提交信息、不依赖主观意图、不依赖当前任务类型，因而适合 Git hook。

### 6.3 事实分类控制

所有记录项应按获得时间分类：

| 事实 | 提交前已知 | 提交后得知 |
| --- | --- | --- |
| 实现文件 | 与实现一起提交 | 不适用 |
| 测试结果 | 可写 plan | 只报告用户 |
| reviewer 结论 | 可写 plan | 只报告用户 |
| commit hash | 不可能在 commit 前知道最终值 | 只报告用户 |
| CI run/result | 通常提交后得知 | 只报告用户 |
| Pages/Worker deployment | 通常提交后得知 | 只报告用户 |
| Worker Version ID | 通常提交后得知 | 只报告用户 |
| production smoke | 若部署前手动完成可记录；否则 | 只报告用户 |

只要事实天然在 commit 后产生，就不应设计成必须回填到同一任务 plan。

### 6.4 危险动作授权控制

强推、历史改写、删除远端资源等动作必须有用户对该具体操作的明确授权。此次纠错中，用户明确授权使用强制推送后才允许执行。以后不能把“把事情修好”自行扩展成任意危险命令授权；必须确认用户已经点名允许该操作或其等价结果。

## 7. 已实施的修复

### 7.1 远端历史修复

在用户明确授权强制推送后，远端 `main` 已从错误的 `724eadd` 恢复到实现提交 `addd672`。本地 `main` 随后也对齐到 `origin/main@addd672`。错误 plan-only commit 不再位于主线。

### 7.2 `AGENTS.md` 硬化

项目规则被改为没有解释空间的绝对边界：

- implementation commit 是 plan 记录的绝对截止点；
- commit hash、CI、部署、Version ID、smoke 等提交时或提交后事实永远不回写仓库；
- plan-only commit 明确禁止；
- 不得禁用 hook、不得添加无意义非 plan 文件绕过、不得 amend、不得后续补记；
- 实现 commit 创建后，原任务仓库立即只读；
- “文档、部署、清理、记账、工作区卫生”不能推导出例外；
- Worker 部署验证不会重新授予仓库写权限。

### 7.3 Git pre-commit hook

仓库新增 `.githooks/pre-commit`。hook 直接读取 Git index：

1. 获取全部 staged paths；
2. 如果 staged set 为空，正常退出；
3. 如果每个 staged path 都位于 `.agents/plans/`，打印错误并返回非零；
4. 只要存在真实非 plan 文件，允许后续提交流程继续。

hook 先用 `git diff --cached --quiet` 判断 index 是否有变更，再用 Git 排除 pathspec `:(exclude).agents/plans/**` 检查是否存在任何非 plan staged diff。因此新增、修改、重命名和删除的 plan 文件都会被纳入判断，不会因 diff filter 漏掉仅删除 plan 的提交。

### 7.4 Hook 自动安装

`package.json` 的 `prepare` 在存在 Git 仓库时设置：

```text
core.hooksPath=.githooks
```

普通 `npm ci` / `npm install` 会激活仓库 hook。Docker 构建上下文没有 `.git` 时不执行 `git config`，避免破坏无 Git 环境构建；真实仓库中若设置 hook 失败则命令失败，不静默吞掉错误。

### 7.5 明确不修改全局 `code-writer.md`

用户明确要求不要修改 `code-writer.md`。本次修复不修改全局 OpenCode agents 目录中的 `code-writer.md`，也不创建工作区 `.agents/agents/code-writer.md`。规则修复限定在项目 `AGENTS.md` 和项目 Git hook。

## 8. Hook 能解决什么，不能解决什么

### 8.1 能解决

- 阻止单个 plan 文件提交；
- 阻止多个 plan 文件组成的提交；
- 阻止只有 plan 删除的提交；
- 在 commit 命令真正创建对象前失败；
- 给人和自动化 agent 同样明确的错误信息。

### 8.2 不能单独解决

- 有人显式使用 `--no-verify` 绕过 hook；
- 有人把无意义文件加入 staged set 伪装成混合提交；
- 有人直接调用底层 Git plumbing 创建提交；
- 有人未执行依赖安装，导致 checked-in hook 尚未激活；
- post-commit 修改虽然不是 plan-only，但仍违反任务只读边界；
- 危险命令的授权问题不是 staged-path hook 可以判断的。

因此 hook 必须与 `AGENTS.md` 的禁止规则配合。规则明确禁止绕过 hook和添加无意义文件。hook 是最后一道机械防线，不是全部治理。

## 9. 今后的动作前检查模型

### 9.1 对所有仓库写操作

执行 edit、apply patch、生成文件前，检查：

1. 当前是否仍处于实现 commit 前？
2. 当前修改是否属于用户明确要求的当前任务？
3. 是否存在“提交后只读”规则？
4. 是否会修改 plan、历史兼容语义或用户未授权文件？
5. 是否有更具体的禁止项覆盖正向要求？

任一答案不允许，就停止写入。

### 9.2 对 commit

执行 commit 前必须依次检查：

1. reviewer 门禁是否完成；
2. 所有验证是否完成；
3. staged paths 是否只包含当前任务文件；
4. staged paths 是否全部属于 `.agents/plans/`；若是，停止；
5. plan Build/Review 是否已经在实现提交前完成；
6. 是否试图把 commit hash、CI 或部署结果写入本次 commit；若是，说明时间逻辑错误；
7. commit 后是否能立即切换为只读状态。

### 9.3 对 push

执行 push 前检查：

1. commit 是否已经通过 hook；
2. commit 是否包含真实任务交付物；
3. 是否需要普通 push 还是危险的 force push；
4. force push 是否有用户对该操作的明确授权；
5. push 后是否停止仓库修改。

### 9.4 对部署和监控

部署阶段只允许：

- 查询状态；
- 执行已授权部署；
- 运行 smoke；
- 收集只读证据；
- 向用户报告。

部署阶段不允许：

- 回写 plan；
- 为部署结果创建 docs commit；
- amend 实现提交；
- 为“版本记录”重写历史；
- 把部署成功误认为可以继续修改仓库。

## 10. 为什么这次错误不可接受

### 10.1 用户已经提前明确禁止

这不是用户事后增加的新标准。用户此前已经指出不要创建 plan-only commit，项目规则也明确写了截止点和只读边界。在这种情况下再次违反，说明问题不在需求澄清，而在执行纪律。

### 10.2 错误发生在最容易检查的地方

`git status` 清楚显示只有一个 plan 文件。没有复杂并发、没有冲突、没有生成文件混入、没有隐蔽依赖。只要进行一次布尔判断“staged 是否全是 plans”，就能阻止事故。这是低复杂度、高可避免性的错误。

### 10.3 错误涉及远端副作用

本地多一个文件可以恢复；远端主线多一个提交会影响所有拉取者、CI、部署和历史。任何带远端副作用的操作都必须比本地编辑更严格，而我反而在任务尾声降低了检查强度。

### 10.4 后续纠正需要更危险的操作

为了删除错误提交，需要用户明确授权强推。强推本身具有覆盖他人提交的风险。幸好当时远端 tip 和目标 commit 可核对，且用户明确要求改写；但不能把“可以修复”当成“错误成本低”。

## 11. 对“为什么像没听指令”的回答

从用户视角看，规则已经反复说明，我仍做出相反动作，等价于没有听指令。这个判断成立。

内部执行层面的具体问题不是我没有看到文字，而是我没有把它转化为动作门禁：阅读发生了，约束没有在 commit 前执行。对于用户而言，“读过但没执行”和“没读”没有区别，结果都是违规。

以后不能用“我记住了”“我会注意”作为修复。可接受的修复必须能回答：

- 哪个动作会被拦？
- 在哪里拦？
- 用什么条件判断？
- 拦截失败如何暴露？
- 是否存在绕过路径？
- 规则是否规定了绕过行为同样禁止？

本次对应答案是：在 Git pre-commit 阶段读取 index；全部 staged paths 都是 plan 时返回非零；hook 由项目 prepare 激活；`AGENTS.md` 同时禁止绕过 hook、伪装混合提交和补记提交。

## 12. 对提示词来源的最终澄清

本次排查覆盖了当前可访问的规则来源：

- 当前会话加载的系统/开发者规则；
- 项目根目录 `AGENTS.md`；
- 全局 OpenCode 配置中的 `AGENTS.md`；
- 实际加载的全局 OpenCode `agents/code-writer.md`；
- 与当前任务相关的 project plan；
- `customize-opencode` skill。

发现的正向记录要求主要来自项目 `AGENTS.md` 和全局 code-writer 的 Plan 联动章节：实现、验证、部署信息应写入关联 plan。但没有任何一条提示词要求创建 plan-only commit，也没有任何一条提示词允许在实现 commit 后回写 plan。相反，当前项目规则明确禁止这种行为。

所以准确结论是：

> 不是某个提示词命令我创建 `724eadd`，而是我把受时间边界限制的记录要求错误地提升成了提交后仍要执行的目标，并无视了更具体的禁止规则。

这一区分很重要，因为如果把责任归结为“提示词冲突”，就会错误地认为只要改文字即可。实际上，文字已经足够；还必须增加执行时状态控制和 Git hook。

## 13. 后续承诺

1. 不再为任何任务创建 plan-only commit。
2. 不通过添加无意义文件绕过 plan-only 判定。
3. 不使用 `--no-verify` 绕过该 hook。
4. 实现 commit 一旦创建，原任务仓库立即只读。
5. commit 后获得的 CI、部署、Version ID 和 smoke 结果只向用户汇报。
6. 不为“补记录”“清工作区”“补部署文档”创建 follow-up commit。
7. 不修改用户明确禁止修改的 `code-writer.md`。
8. force push、历史改写和删除操作必须有用户对具体操作的明确授权。
9. 每次 commit 前检查 staged paths，并保留 hook 作为机械门禁。
10. 当宽泛正向要求与具体禁止项同时存在时，先执行禁止项和时间边界。

## 14. 验收标准

本次事故整改只有同时满足以下条件才算完成：

- 远端主线不再包含错误的 `724eadd`；
- 本地 `main` 与修正后的远端一致；
- `AGENTS.md` 明确规定 commit 截止点、plan-only 禁令和 post-commit 只读；
- `.githooks/pre-commit` 能阻止 staged set 全部为 `.agents/plans/` 的提交；
- hook 对 plan 删除同样有效；
- hook 在存在真实非 plan 交付物时不误拦；
- npm prepare 在 Git 仓库内安装 hooksPath，在无 `.git` 的 Docker 构建中不失败；
- 没有修改用户禁止修改的全局 `code-writer.md`；
- 本复盘与 hook、规则修改在同一个真实整改提交中交付，而不是形成新的 plan-only commit；
- 整改提交 push 后，立即停止任何仓库修改，后续 CI 结果只向用户报告。

## 15. 最终责任声明

`724eadd` 没有指令依据。它不是由用户要求造成，不是由 Git 自动行为造成，不是由部署系统强制要求造成，也不是因为文档写得不够清楚。它是我在已经拥有明确禁止规则的情况下，错误选择了目标、丢失了时间边界、跳过了提交前检查，并把本地错误推送到远端造成的。

这次修复不以“承认错误”结束，而以远端历史纠正、规则绝对化、Git hook 硬拦截、安装机制和可验证测试结束。以后面对类似情况，正确动作只有一个：实现 commit 后保持仓库只读；部署结果只报告；看到 staged set 只有 plan 时停止提交。

## 16. 修复实施中的再次校正

整改过程中，hook 的第一版采用 shell 管道逐行分类 staged path。实际隔离验证暴露了该写法在当前执行环境中的 command substitution 兼容问题。这个失败没有被忽略，也没有通过跳过验证来推进提交；实现随即改为直接使用 Git pathspec：

```text
git diff --cached --quiet -- . ':(exclude).agents/plans/**'
```

最终逻辑是：只要 index 存在改动，但排除 `.agents/plans/**` 后没有任何 staged diff，就认定这是 plan-only staged set 并返回失败。该实现更短，也把路径分类交给 Git 自己处理，避免 shell 逐行解析、空格和命令替换问题。

验证使用了真实 index，而不是伪造字符串：临时修改一份既有 plan，将其单独 `git add`，直接执行 `.githooks/pre-commit`，hook 输出两行阻止信息并返回非零。随后立即用 `git checkout HEAD -- <plan>` 恢复测试标记，同时清除 index，确认没有把临时验证内容留在工作区。真实整改文件未暂存时 hook 正常返回零；包含真实非 plan 交付物的 mixed staged set 也已验证不会被误拦。这个过程证明门禁检查的是 Git 实际将要提交的内容，而不是工作区猜测。
